Lesson 2 · Git for Vibe Coding The agent's sandbox

Lesson 1 gave you a way to catch bad work before it commits. But long sessions break that: the agent commits on its own, and main quietly accumulates experiments. This lesson moves the experiments off main — onto branches that can disappear — and replaces “should I keep this?” with a two-way decision: merge or kill.

Warm-up (30 seconds, from Lesson 1) — name two things git restore . can’t undo.

Anything already committed — restore only touches your uncommitted files — and anything on a branch that’s already been deleted. Both are exactly what a long agent session produces. That gap is the whole problem this lesson closes.

1The loop’s blind spot

Lesson 1’s loop is strong against uncommitted mess: git restore . and it’s gone. Two things in a real afternoon break that assumption:

Time. Review → commit → prompt → repeat. Three hours in, main holds fourteen agent commits, some of them only glanced at. Now commit 3 was subtly wrong, and “roll back” means rewinding eleven commits — which restore . can’t touch at all.

Auto-commits. Many agent tools commit for you (auto-checkpoints, “commit and continue”). The moment the agent commits, your 30-second full rollback no longer exists.

The fix is not “never let the agent commit.” It’s giving the work a place that can disappear.

2The sandbox model

Three rules, and that’s the whole model:

1. main is the only work you chose to keep. The agent never builds directly on it. main is the safe line — the last thing you’d happily ship.

2. A branch is a draft. Drafts are cheap: git switch -c moves a pointer and changes nothing in your files (branches are moving pointers, not copies of the code — that’s the primary read at the end of this lesson).

3. Every branch has exactly two exits: merged into main, or deleted. There is no third state. “I’ll keep it around just in case” is branch limbo — the graveyard where half-dead experiments pile up and start to scare you.

A ── B ── C ─────────────────── M
          │
          ├─ wild-idea:  D ─ E ─ F      killed — main never noticed
          │
          └─ add-search: G ─ H ─┘       merged, then deleted

M is a merge commit — the only place a branch becomes main. Everything else on the right of C is a draft, and every draft gets a decision.

Key idea The agent works on the branch. It can wreck, auto-commit, experiment freely — the blast radius is the branch. main can’t be hurt. The checkpoint loop from Lesson 1 still runs, but now it runs inside the sandbox, at the end of the branch: diff it against main, then merge or kill.

3The commands

You want to…Type…Note
start a new draftgit switch -c <name>create + switch in one step. (Old spelling: git checkout -b <name>.)
go back to the safe linegit switch mainyour files snap back to main’s state — the branch’s mess simply isn’t here
see everything a branch didgit diff main...<name> --statthree dots = everything the branch added relative to where it left main. This is your branch-scale diff gate.
bring the branch into maingit merge --no-ff <name>--no-ff keeps the branch’s commits as one labelled hump in the log — if you regret it later, you can revert the whole feature in one command.
delete a branch you mergedgit branch -d <name>lowercase -d is safe: it refuses to delete anything unmerged. A built-in guard.
kill a branch on purposegit branch -D <name>uppercase -D = I mean it. This is the kill button.
back up a long experimentgit push -u origin <name>a remote copy, in case your laptop dies mid-idea. It is not a “keep” decision — the remote branch dies when the branch does.

4The merge-or-kill gate

When the agent finishes its branch, you don’t feel a decision, you run one. Three questions:

1

Does it work?

Run the app, run the tests. The branch’s latest state, not a memory of how it looked.

2

Does the diff match the ask?

git diff main...<name> against the words of your original prompt. Lesson 1’s red flags apply here, at branch scale.

3

Can you explain it in one sentence?

If you can’t, you don’t understand what you’re about to merge — and merging is how a branch becomes permanent.

All three yes → merge: git merge --no-ff <name> on main, then git branch -d <name> (it works because it’s merged).

Any no → kill: git switch main && git branch -D <name>, then re-ask the agent with a tighter prompt. The branch and all its commits disappear together. Ten seconds.

The trap this gate is built for “…but the agent spent forty-five minutes on it.” That time is sunk — the only costs that still exist are: 10 minutes to delete the branch, versus hours to debug code you don’t trust. The agent’s effort is not yours to avenge. Its work is a draft, not an asset — and drafts get killed all the time. That’s what drafts are for.

One exception: hand-picking some of the files (surgery) is worth it only when the kept part is genuinely costly to re-derive — a long test suite, a data migration. Even then, verify the picked part in isolation. The default is whole-branch: merge or kill, never half-keep.

5Guardrails for the agent

The sandbox is only as real as the fences around it. Four settings, once per tool, then you never think about them again:

• Name the branch in the prompt. “Work on branch add-search. Do not touch main.” Most agents respect an explicit instruction about where they’re standing.

• Forbid the scary merges. In your tool’s settings: no auto-merge into main, no auto-push to main, no force-push. (Same guardrail list as Lesson 1 — now it matters at branch scale.)

• Allow auto-commits on the branch. This is the twist from Lesson 1: agent auto-commits are fine inside the sandbox. They’re draft checkpoints — and they actually make the kill decision easier, because you can inspect the individual commits in the diff.

• You own merge and delete. The agent may commit; only you merge, and only you delete. That split — agent drafts, you decide — is the whole operating model this course is built on.

7Practice — do this now

Ten minutes, throwaway folder. This rep is the whole lesson — one wasted draft, one good one:

mkdir vibe-sandbox && cd vibe-sandbox && git init
# a tiny working app
git add -A && git commit -m "working app"

# 1 — a wild experiment
git switch -c wild-idea
# ask your agent: "rewrite this app however you think is best"
# (let it auto-commit as much as it likes — it's a draft)
git diff main...wild-idea --stat   # the map of the damage
# → fails the gate → kill:
git switch main && git branch -D wild-idea    # gone. main never noticed.

# 2 — a scoped ask
git switch -c add-search
# ask for ONE small feature: "add search to the list. UI only, touch nothing else."
git diff main...add-search --stat  # the gate: works? matches? explainable?
# → passes → keep:
git merge --no-ff add-search
git branch -d add-search           # safe -d works because it's merged
git log --oneline                  # ← the hump: the draft, now part of main
Or practice with me Tell me: “make a mess in a scratch repo.” I’ll set up the working app, then have the agent genuinely wreck a wild-idea branch. You run the kill, the scoped re-ask, and the merge — I’ll watch every command and check them against the gate. Tightest feedback loop available.
