Lesson 5 · Git for Vibe Coding The remote

You watched the remote happen for real: git init, one commit, remote add origin, push -u — and the whole course is now on GitHub. This lesson names what that actually did, and dissolves the word that makes git feel scary: origin is a copy, not a boss. By the end, every command you have learned has a home in one picture.

Warm-up (30 seconds, from Lesson 4) — a bad commit has already left your machine. Which door, and which command?

Cancel — git revert <sha>: a new commit that undoes it. History intact, every clone consistent. Shared history gets cancelled by new commits, never rewritten. That sentence gets its mechanism in this lesson — and it's the reason for everything origin does.

1origin: a copy, not a boss

Here is the real transcript from when we connected this course to GitHub — your remote now, this lesson's example:

git init -b main
git remote add origin https://github.com/kecai/learngit.git
git push -u origin main

What push did: it copied your commits to a server. It did not move them, hand them over, or start reporting to anyone. Your repo on this machine is still the live one — the place where files actually get edited. The repo on GitHub is a snapshot of what you chose to share, updated only when you say so.

For a solo developer the remote is two things: a backup (your work survives a broken laptop — this course now does) and a mailbox (a way for you-on-another-machine to get a copy). It is not a third place where “the real code lives.” If that phrase is starting to feel true, stop — un-teaching that feeling is what this lesson exists for.

The single-player model You (machine A) ⇄ GitHub ⇄ you (machine B, one day). Every arrow is a copy operation you trigger. Nothing syncs on its own; nothing watches you. push -u (Lesson 2, one line) only set a default address: from now on, bare git push and git pull know which remote and which branch, without a URL.

2Ahead and behind — the one line to read

git status reports your branch against its remote twin in exactly one line. The whole remote dance is reading that line:

The line says…It means…The move
“up to date with 'origin/main'”both copies tell the same storynothing
“ahead by 2 commits”you hold 2 commits the server copy lacks — an unsent queuegit push
“behind by 3 commits”the server copy holds 3 commits you lack — an unread queuegit pull
“diverged” (both)both queues exist — both sides grewgit pull → Lesson 3

The four commands, and what each actually touches:

CommandServer → youYou → serverTouches your working tree?
git fetchdownloads missing commits—no — bookmarks only
git pulldownloads, then merges them in—yes — it runs a merge (L3)
git push—uploads your commitsno
git clonecopies the whole repo, once—creates a new folder

The un-teaching: pull is not a mystery verb. It is fetch + merge — the Lesson 3 merge with a download bolted on. Every scary thing a pull can do, you already know how to end.

3Behind has two kinds (two exits, no limbo)

“Behind” hides a fork in the road. Before you pull, know which kind of behind you're in:

Your branch is…Pull doesMerge commit?Can it conflict?
strictly behind — you made no commits since the forkfast-forward: the pointer slides forward along existing historynono — one line of history, nothing to disagree with
diverged — you and the server both grewa real merge of the two historiesyesyes → Lesson 3's two exits: finish or abort
The costume change Lesson 2: merge-or-kill. Lesson 3: finish-or-abort. Lesson 5: a pull has no exits of its own — only the diverged kind has decisions. Strictly behind is not an operation, it's a free lunch. Check the status line first; the scary kind is the one with your own commits in it.

4What push refuses

Push has one law: a branch may only move forward. It can create a branch, or advance it with new commits — never remove history the server holds. Try it: rewind past a commit that's on origin, then push.

$ git reset --hard HEAD~1    # rewind past a pushed commit
$ git push
To https://github.com/kecai/learngit.git
 ! [rejected]        main -> main (non-fast-forward)

That rejected line is Lesson 4's shared-history door with its mechanism: origin doesn't know about your rewind, and “pushing” would mean erasing a commit someone — you, on machine B — may hold. Git stops and explains instead of burning it.

The override exists — git push --force — and it does exactly what the law forbids. That's the fire exit, now with a why behind it: never an agent's command, ever (Lesson 1's guardrail, understood rather than memorized). The habit version, for the one day it becomes legal on your own private repo (Lesson 6): --force-with-lease — it refuses if the server moved since your last fetch.

5The agent at the remote

The remote is where “shared” begins — even solo. The moment you push, a copy exists that another-you will pull. So the publishing gate from Lessons 1 and 4 applies one rung up: the agent prepares, you ship.

CommandThe agent may…Because
git fetch · git status · git log origin/main..mainrun freelydownloads and reads; moves nothing you can see
git pullrun — when the line says behindbut a diverged pull opens Lesson 3's exits — those are yours
git pushprepare the commits — you pushpublishing is the human's trigger, like the commit was in Lesson 1
--force / --force-with-leaseneverthe fire exit: L1 guardrail + L4 “burns every clone”, cited twice

Delegate the reading, keep the publishing. An agent that reports what the server has (“origin is 3 ahead — here's the diff”) is a good one. An agent that does the push has skipped a rung.

6Check yourself

Four scenarios from real remotes. Options shuffle each load — click for instant feedback.

Q1. git status says: “Your branch is ahead of 'origin/main' by 2 commits.” What does that mean?

Q2. You ran git pull. Your branch is strictly behind origin — no commits of your own since the fork. What happens?

Q3. You ran git reset --hard, undoing a commit that is already on origin. What does git push do next?

Q4. You're about to let the agent touch the remote. Which command is safe to let it run unattended?

3 or 4 correct and the remote has stopped being scary. Q3 is the one that separates “I can push” from “I know what push refuses” — if that one stung, tell me and we'll drill it.

7Practice — two machines

Fifteen minutes, on your real repo. Two clones act as two of you:

# Machine B — a second clone, in a sibling folder
cd ~/dev/ai
git clone https://github.com/kecai/learngit.git learngit-b
cd learngit-b
# …one small edit, committed, pushed      (server now 1 ahead of A)
cd ..

# Machine A (this folder)
git pull            # ← kind one: fast-forward. No decision was even possible.
# …one edit of your own, committed        (now: diverged)
git pull            # ← kind two: a real merge — Lesson 3's two exits, live

When you finish, both clones say “up to date” — and the repo on GitHub agrees with both. Three copies, one story. That agreement is the entire game of the remote.

Or practice with me Tell me: “run the two-machine drill.” I'll create the second clone, make it ahead, and push — then you run the pulls and I check every command. When the divergence bites, we run Lesson 3's exits on it together.
Primary source — read today Pro Git, “Remote Repository Management” — git-scm.com/book. Ten minutes. It turns today's four commands into understood machinery: remote add/list/remove, what the -u tracking flag stores, and the one-paragraph definition of pull you'll never un-know (fetch + merge).
