Lesson 3 · Git for Vibe Coding When main moves underneath you

Lesson 2’s sandbox had one quiet assumption: main is still where you left it. It isn’t — you merged a branch, you pulled, a week passed. Branches diverge, and when two sides both touched the same lines, git stops and asks you a question. This lesson: what a conflict actually is, the loop for finishing one, the one command that unwinds all of it — and the role your agent plays (interpreter, not resolver).

Warm-up (30 seconds, from Lesson 2) — a branch has exactly two exits. Name them, with the command for each.

Merged — git merge --no-ff <name> (then git branch -d) — and killed — git branch -D <name>. No third state. That “two exits, no limbo” rule is about to show up again, because it’s the spine of this lesson too.

1Main moves. That’s normal, not a failure.

Three ways main ends up ahead of your branch:

• You merged your last branch into main (Lesson 2’s move) and started the next one from the new main — fine. But if you’d started the new branch before that merge, it now sits behind.

• You pulled or pushed elsewhere — solo devs diverge too; there’s no “someone else” required.

• Your branch is old. A branch started three weeks ago doesn’t know about anything that landed on main since.

None of this is a problem until you try to bring the two sides together and both of them edited the same lines differently. That’s the one case git refuses to handle for you.

2Divergence, drawn

A ── B ── C ─────────── E ─ F     ← main moved: two new commits after the fork
          │
          ├─ D ─ G               ← your branch, built on the old C

main and your branch are both ahead of C.
Neither side is wrong. They just don’t know about each other yet.

Reconciling has two directions, and they cost the same work at different times:

DirectionCommand (on your branch)When the conflicts hurt
Bring main into the branch — git merge mainnow, while the branch is small and the work is fresh in your head
Bring the branch into main — git merge --no-ff <name>at the end, possibly with weeks of drift packed into one big diff
The rule Sync early, not late. Same total work, but early conflicts are small and localised; late conflicts are an archaeology dig. When a branch starts feeling stale, git merge main into it — that’s maintenance, not a decision.

Note: on a feature branch, git pull pulls the remote of the current branch — not main. The tool for “main moved” is a plain git merge main.

3The conflict: git refusing to guess

A conflict is not an error. It’s git saying: “both sides changed these lines, in different ways, and I will not guess which intent wins.” It stops the merge, marks the files, and hands you the judgment. The marker:

app.js — the conflicted hunk
<<<<<<< HEAD
  const label = "Log in";
=======
  const label = "Sign in";
>>>>>>> main

Top side = you (where you were when the merge started). Bottom side = incoming (main). For each hunk, exactly three legal moves:

• Take the top. Your change was the intended one.
• Take the bottom. Main’s change was the intended one; yours was a stale duplicate of the same idea.
• Write a third line that fuses both intents — the honest move when both changes are real and compatible.

Notice what none of this is: it is not a text problem. “Which side is right” is an intent question — what was each change for? That is the only question in all of git that only you can answer, which is why the agent guardrails in section 5 matter most here.

4The conflict loop

1

Map the damage

git status lists every conflicted file (“both modified”). That list is your to-do list — nothing else in the repo is affected.

2

Read each hunk

Open the file, find the <<<<<<< markers. (Section 5: your agent can translate each hunk into plain English first.)

3

Decide, per hunk

Top, bottom, or a fused third line. The call is about intent, and it’s yours.

4

Mark it resolved

git add <file> after each file. “Resolved” literally means “staged” — git has no other concept of done.

5

Finish the merge

All files added → git commit (or git merge --continue). The merge commit records that the two sides were reconciled — your decisions are now history.

Two exits, again A merge is either finished (add + commit) or aborted: git merge --abort — and you are back to exactly the state you were in before you typed the merge. Nothing is lost; it’s as if the merge never happened. There is no third state. A repo left mid-merge overnight is branch limbo with extra steps — always pick an exit, even if the exit is “not today.”

5The agent as conflict interpreter

Conflicts are the one place in vibe coding where the agent’s default behaviour is actively dangerous. Left unsupervised, an agent “resolving” a conflict usually means: pick one side wholesale, keep moving. It has no way to know your intent — it’s pattern-matching on syntax, and syntax can’t tell you whether the rebrand to “Sign in” was the point.

The working division of labour — agent interprets, you judge:

The prompt that works “Don’t resolve anything yet. For each conflicted file, show me each hunk in plain English: what does the top side do, what does the bottom side do, and do the two changes conflict in purpose or just in text?”

You then make the calls — usually in under a minute per hunk, because the agent did the translation. Red flag: the agent “fixed” a conflict by deleting one side wholesale without you reading it. That’s a guess wearing a costume; re-run with the prompt above.

Conflicts are the rare moment to deliberately slow down in an agent session. Everything else in this course is about moving faster with less fear; a conflict is where the fear is earned — it’s the one decision git insists on making human.

6Check yourself

Four scenarios. Options shuffle each load — click for instant feedback.

Q1. You run git pull on main and it ends with a conflict. What state is the repo in?

Q2. You’re on your feature branch. Meanwhile main got two new commits (you merged another branch earlier). You want main’s changes in this branch, now. What do you type?

Q3. Conflict in copy.js: your branch has "Log in", main has "Sign in". Main changed that line two weeks ago (a rebrand). You never intended to change that line. What do you keep?

Q4. You’ve edited every conflicted file and saved. The merge still isn’t finished — git status still says “fix conflicts.” What completes the merge?

3 or 4 correct and you can stand in a conflict without fear. Q1 or Q4 shaky? Those are the two states everyone panics in — tell me which, and we’ll drill it.

7Practice — do this now

Ten minutes, no agent needed — this lesson is about you making the call. You manufacture the divergence by hand:

mkdir vibe-diverge && cd vibe-diverge && git init
# app.js containing one line:   const label = "Log in";
git add -A && git commit -m "working app"

# fork the branch, do UNRELATED work on it
git switch -c fix-copy
# change the button colour in app.js (any unrelated line)
git add -A && git commit -m "button colour"

# meanwhile, main moves — edit the SAME label line
git switch main
# edit app.js:   const label = "Sign in";
git add -A && git commit -m "rebrand button text"

# now bring main into the branch → conflict
git switch fix-copy
git merge main          # ← BOOM: "merge conflict" in app.js
git status              # the map: which files are conflicted
# open app.js, find <<<<<<< — keep main's "Sign in" (the rebrand was the intent)
git add app.js
git commit              # merge finished. Two exits; you took one.
git log --oneline --graph   # ← the hump where the two sides met
Or practice with me Tell me: “make a mess in a scratch repo” — I’ll set up the divergence, have the agent edit the same lines on both branches so the conflict is real, then run the interpreter prompt for one hunk as a demo. You make the calls and drive the loop; I watch every command.
Primary source — read today Pro Git, “Merging” (the resolving-conflicts sections) — git-scm.com/book. Ten minutes. It turns the markers above from scary sigils into machinery: you’ll see exactly why git can auto-merge most hunks, why “both modified” is a precise state, and where --abort fits in the sequence.
