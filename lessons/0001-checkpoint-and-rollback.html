Lesson 1 · Git for Vibe Coding Git is your undo button

In vibe coding, the agent writes the code. You control the state — and git is the only thing between “working app” and “agent experiment that broke everything.” This lesson installs one habit: the checkpoint loop.

Warm-up (30 seconds, from memory) — what does git commit actually save?

A snapshot of everything you staged with git add — a frozen photo of those files at that moment. Not “the changes,” not the whole project: the staged state, plus a message. (You said you know git basics — this probe checks how solid the foundation is. If that answer felt shaky, ask me to re-drill it before going on.)

1Why this lesson

“There's a new kind of coding I call 'vibe coding', where you fully give in to the vibes, embrace exponentials, and forget that the code even exists… I 'Accept All' always, I don't read the diffs anymore.”

— Andrej Karpathy, who coined the term, Feb 2025 (@karpathy)

One year later Karpathy revised his own position: agent-driven programming is now a professional default, “except with more oversight and scrutiny” — his current favourite name for it is agentic engineering (a Feb 2026 retrospective). The gap between the two tweets is exactly what this course closes: the difference between giving in to the vibes and engineering with agents is oversight — and git is the oversight tool.

Key idea You are no longer the typist. You are the state controller. The agent moves files around fast and makes mistakes fast. Git is your save system, your undo button, and your audit log. One loop does all three.

2The checkpoint loop

1

Start clean

git status — anything you were working on gets committed first. Rule: never let the agent start from a dirty tree. Otherwise, after it finishes, you cannot tell which changes are yours and which are the agent’s.

2

Agent works

Prompt, walk away. The agent edits whatever it likes. This is the fast part — you don’t babysit keystrokes.

3

The diff gate

When it’s done: git diff --stat for the map, then git diff <file> for the suspicious ones. Nothing gets committed until you’ve read what changed. This is the “more oversight and scrutiny” step.

4

Keep or roll back

Good → git add -A && git commit -m "what you actually asked for". Bad → git restore . (all of it) or per-file. Then back to step 1 with a tighter prompt.

The whole loop costs you 30 seconds of attention, repeated. That repetition is the skill. It turns “the agent broke my app” from a disaster into a shrug: git restore . and re-ask.

3Reading a diff (the minimum viable version)

You don’t need to read every line the agent touched. You’re hunting for intent drift — changes that don’t match what you asked for. A diff is red lines (removed) and green lines (added):

--- a/app.js   +++ b/app.js
-  const maxAttempts = 3;
-  if (attempts > maxAttempts) throw new Error("locked");
+  const maxAttempts = 999999; // be generous
+  // TODO: remove rate limiting later?

git diff --stat gives you the map first — files touched plus lines added/deleted. Four red flags worth stopping for:

Red flagWhat it smells like
Deletions far exceed additionsIt ripped something out to make its change fit
Files you never mentioned (config, package.json, lockfiles, .env)Scope creep — or it’s about to leak your secrets
Red lines that were safety checksIt deleted the guardrails to make a bug disappear
“Refactor” across 20 files for a one-line askTrust-but-verify failed; this needs a full read or a rollback

If a diff passes all four checks and the app works, you’ve reviewed it. That’s the bargain: minutes of scrutiny, not hours of line-reading.

4The undo toolbox

Five commands cover virtually every “oops” in vibe coding. The column that matters is what it touches — that’s what makes one safe and another nuclear.

You…Type…It touches
want to discard one file’s uncommitted changesgit restore <file>that file only, back to the last snapshot
want to discard all uncommitted changesgit restore .every modified file — your 30-second full rollback
staged something by accidentgit restore --staged <file>the index only — file content untouched
committed bad work, not pushed yetgit reset --hard <commit>working tree + index + branch pointer. Nuclear — local only.
committed bad work, already pushed / sharedgit revert <commit>adds a new commit that undoes it. History stays intact; safe for anyone with a clone.
Goldilocks In vibe coding, ~90% of recovery is git restore — because the loop keeps bad work uncommitted. The undo commands that move history (reset, revert) are your backup plan, not your daily driver. Find your checkpoints with git log --oneline; compare against them with git diff HEAD~2.

5Check yourself

Four scenarios, straight from real vibe-coding sessions. Options shuffle each load — no positional hints. Click an answer for instant feedback.

Q1. The agent just rewrote four files and now the app crashes. Nothing is staged or committed. What do you type first to see what it did?

Q2. The diff shows the agent mangled auth.js. The other three files look fine. Nothing is staged or committed. You want to discard only auth.js. What do you type?

Q3. You asked for one small change. The diff shows 12 lines added, 340 deleted, and it touched .env (your secrets). What do you do?

Q4. Mid-session, the agent finishes a feature, the app works, and your diff check found nothing suspicious. What do you do next?

3 or 4 correct and you’re ready for the practice step. Below that? Ask me to walk through any scenario — that’s what I’m here for.

6Practice — do this now

Six steps, ~10 minutes, in a throwaway folder. This is the rep that makes the loop a habit:

mkdir vibe-practice && cd vibe-practice && git init
# create app.js — any tiny script that runs, e.g. prints "v1 works"
git add -A && git commit -m "working app v1"
# NOW: ask your agent to make a deliberately bad change to app.js
git status            # see what it touched
git diff --stat       # the map
git diff app.js       # the actual change
git restore app.js    # roll it back
# ask the agent for a GOOD change instead → diff →
git add -A && git commit -m "add the good change"
git log --oneline     # ← two clean checkpoints. That's the habit.
