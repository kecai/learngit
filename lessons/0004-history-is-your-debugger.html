Lesson 4 · Git for Vibe Coding History is your debugger

The agent writes fast. A long session leaves “it was working yesterday” 30 commits in the past — and the tree is still moving while you debug. This lesson turns history into a machine you point at: find the last known-good commit, diff the range, and let git bisect name the guilty one in about five answers. The skill is not the commands — it’s knowing what to point them at.

Warm-up (30 seconds, from Lesson 3) — a merge has two exits. Name them, with the command for each.

Finished — git add every conflicted file, then git commit (or git merge --continue). Aborted — git merge --abort, back to exactly the pre-merge state. That rule — every operation ends, nothing lingers — comes back in this lesson wearing a different costume.

1It was working yesterday. That’s 30 commits ago.

Lesson 1’s loop covered ~90% of recovery, because it kept bad work uncommitted: git restore . and it was gone. Long sessions break that — auto-commits, an agent that commits on its own, a feature that took three prompts. By afternoon, main holds thirty agent commits, some of them only glanced at. And the app breaks.

The pre-agent debugging habit fails here for a specific reason. The habit is: open the file, read the current code, reason about why it fails. But the current code is a blend of thirty unreviewed decisions — and you cannot tell which line is yours, which is the agent’s, or which one caused the crash. You are debugging fog.

The reframe Stop debugging the present and start interrogating the history. Git keeps a frozen snapshot of every state the repo has ever been in. Your working tree is where you live; history is where the evidence is. The commands in this lesson are few and stable — the skill is knowing what to point them at: a good commit, a range, a failing test.

2The time-travel gate

When the app breaks, don’t start with a command — start with one question: what was the last commit you know was good? You know, because Lesson 1’s habit made your checkpoints tested states, not just saved ones. Then run three steps:

1

Find the last good

git log --oneline — one line per commit, newest first. Add --stat for the map: which files each commit touched. Locate your checkpoint: “it was working at C.”

2

See the delta

git diff <C>..HEAD --stat — thirty commits collapse into one map of everything that changed since the last good. Then, per suspicious file: git diff <C>..HEAD -- <file>. Thirty mysteries become one readable diff.

3

Ask the agent, with evidence

Now — and only now — hand the agent the delta and the failure output. It reasons from evidence instead of vibes. (Section 5 has the exact prompt.)

Two dots: “what changed between these two commits.” When the two commits sit on one straight line, the two-dot and three-dot forms agree — pick one and stay consistent. (Three dots on a branch name meant “relative to where it left main” — that’s Lesson 2’s tool.)

The gate in one line Find the last good → diff the range → then talk to the agent. The order is the lesson. Reverse it — agent first, evidence later — and you get vibes with extra steps.

3The two doors of undo

Suppose the delta points the finger — or bisect, next section, does. You now have a guilty commit. Lesson 1’s undo table still applies, but the choice of door now depends on one question the table didn’t need: has the bad commit left your machine?

The guilty commit is…DoorCommandWhat it does
local-only — never pushedrewindgit reset --hard <C>Moves the branch pointer back; the bad commits vanish from this branch. Only safe while nobody else has a copy. (Lesson 1’s nuclear option — now aimed at a specific commit.)
pushed / sharedcancelgit revert <sha>Adds a new commit that undoes the bad one. History intact; every clone stays consistent.
a whole merged feature (a --no-ff hump)cancel the humpgit revert -m 1 <merge-sha>One new commit that undoes the entire feature — paying off the promise Lesson 2 made when it told you to merge with --no-ff.
Two exits, third time A bad commit has exactly two doors, and the choice is one question: has it left your machine? Local → rewind. Shared → cancel. “Force-push the rewind” is not a third door — it’s the fire exit, and it burns every clone: your next pull, and every teammate’s. The rule: shared history gets cancelled by new commits, never rewritten. And remember the sandbox: most agent mistakes never reach these doors at all — they die on the branch (Lesson 2’s kill). These doors are for work that survived the gate.

4Bisect — binary search, you as the sensor

Sometimes you have no good anchor — the checkpoint habit failed, or the bug predates your last one — and the delta is unreadable: thirty commits, twenty files. What you do have is exactly what git bisect eats: a state that works, a state that doesn’t, and a test that tells them apart.

git bisect start
git bisect bad HEAD           # “now” is broken
git bisect good <last-good>   # “this commit” still worked

# git checks out a MIDDLE commit — the files on disk are now that past state
# (detached HEAD: you are visiting history, not living in it)
$ node app.js                 # run the test yourself…
git bisect bad                # …and answer. Or good. Repeat.

# …until git names the culprit…
git bisect reset              # back where you were; the guilty commit is named, not lost

Every answer halves the suspect range. Thirty commits → about five test runs, not thirty reads. When one commit remains, git says “commit abc12… is the first bad commit” and shows it — the message, the diff — everything you need to hand to the agent.

WordIt says
startopen the search — refuses if the tree is dirty (Lesson 1’s clean-tree rule, again)
bad <ref>this end is broken (no ref = the commit currently checked out)
good <ref>this end still works
run <test-cmd>answer for me: exit 0 = good, 125 = “can’t test this commit, skip it”, anything else = bad
resetclose the search, return to your branch

The fully automatic version: git bisect run node test.js — git runs the test itself at every midpoint and you watch the count shrink. One honesty note: bisect is a machine. It finds the first bad commit within the anchors you give it — a stale “good” anchor (one that was actually already broken) leads to the wrong culprit. That’s why step 1 of the gate says run the good commit, not assume it.

5The agent in archaeology

Your agent is an excellent diff reader and fix-proposer. Given the range diff and the failure output, it will usually identify the guilty commit faster than you can — and often propose a good fix. The working division of labour is the same shape as Lesson 3’s: you point, it reads, you judge.

The prompt that works “Here is the diff between the last known-good commit and HEAD, and here is the failure output. Which commit most plausibly caused it? Show me that commit’s diff and propose a minimal fix. Don’t change anything yet.”

Then the proposed fix goes through the normal gate — Lesson 1’s diff red flags, Lesson 2’s merge-or-kill. A fix that “makes the symptom go away” is still a diff that has to be read.

Red flag (Lesson 1, recurring): the fix’s diff deletes the safety check that was raising the error. The crash disappears; a silent rot is born. If the proposed fix touches a guardrail line — stop. That’s not a fix, that’s silencing, and only you can know the check was load-bearing (Lesson 3: intent).

And let the agent write the bisect run test command — but “does this command actually fail on the bug and pass on good?” is yours to verify. The archaeology loop, complete: you find → it reads → you gate → it fixes → you gate again. The agent adds speed to every step except the one that requires intent.

6Check yourself

Four scenarios from real broken sessions. Options shuffle each load — click for instant feedback.

Q1. The app worked yesterday. Today it is broken, and thirty agent commits sit between. What do you do first?

Q2. You found the guilty commit. It is already pushed to origin — other clones have it too. How do you undo it?

Q3. You have a last-known-good commit, a broken HEAD, and a failing test command that exits non-zero on the bug. Thirty commits in between. What now?

Q4. The agent proposes a three-line “fix” that makes the crash disappear. You read the diff: one deleted line was a safety check. What do you do?

3 or 4 correct and the time-travel gate is installed. Q2 is the one that separates “I know undo” from “I know shared undo” — if that one stung, tell me and we’ll drill it.

7Practice — do this now

Fifteen minutes, no agent needed — you manufacture the regression by hand, because the rep is the point:

mkdir vibe-bisect && cd vibe-bisect && git init
# app.js — a tiny script whose “test” is: does it print "v1 works"?
# (e.g. node app.js — any runnable thing with an obvious good/bad output)

git add -A && git commit -m "working app v1"      # ← last known good

# v2 — an innocent change (a log line, a comment, a tiny feature)
git add -A && git commit -m "v2: add a log line"

# v3 — the bug: remove the guard line, so the app now crashes
git add -A && git commit -m "v3: tidy up app.js"

git log --oneline                  # v3 ← HEAD (broken) … v2 … v1 (good)
git diff <v1>..HEAD --stat         # gate step two: the whole range, one map

git bisect start
git bisect bad HEAD
git bisect good <v1>
# git checks out a midpoint — run: node app.js
git bisect bad                    # …answer until git names v3
git bisect reset                  # back on your branch; v3 is named, not lost

git revert <v3>                   # the shared-safe door: a NEW commit on top
git log --oneline                 # ← the undo commit, history intact, app well

With three commits, bisect is almost trivial — the drill is the ritual: the gate, the anchors, the answers, the reset, the door. In a real thirty-commit session that same ritual is the difference between five test runs and an afternoon.

Or practice with me Tell me: “make a mess across commits.” I’ll plant a real bug across a dozen or so commits in a scratch repo — a few of them plausible refactors, so the range diff is genuinely ambiguous. You run the gate and the bisect; I check every command. The agent-era variant of every practice so far.
