The compressed version of Lesson 3. One page: the diagram, the loop, the two exits. Pin it with the loop and sandbox sheets.

1Divergence, drawn

A ── B ── C ─────────── E ─ F     ← main moved after the fork
          │
          ├─ D ─ G               ← your branch, built on the old C

Both sides ahead of C. Neither wrong. They just don’t know about each other.
DirectionCommandConflicts hurt…
main → branch (sync, do this early)git merge main (on the branch)now — small, localised
branch → main (the Lesson 2 merge)git merge --no-ff <name> (on main)late — the big diff

git pull on a feature branch pulls its remote, not main. “main moved” = plain git merge main.

2Anatomy of a conflict

<<<<<<< HEAD      ← top: your side (where the merge started)
  const label = "Log in";
=======
  const label = "Sign in";      ← bottom: incoming (main)
>>>>>>> main

Per hunk, exactly three legal moves: take top · take bottom · write a fused third line. The question is intent (“what was each change for?”) — a question only you can answer.

3The conflict loop (two exits, no limbo)

1

Map

git status — “both modified” files are your to-do list.

2

Read

Each hunk, or the agent’s plain-English translation of it.

3

Decide

Top / bottom / fused — your call, per hunk.

4

Mark resolved

git add <file> per file. “Resolved” literally means “staged”.

5

Finish

git commit (or git merge --continue) — the merge commit records it.

The two exits Finish = add every conflicted file + commit. Abort = git merge --abort → exactly the pre-merge state, nothing lost. Never leave a merge hanging overnight — pick an exit, even “not today.”

4Agent guardrails (strongest here)

• Agent interprets, you judge. Prompt: “Don’t resolve yet — for each hunk: what does the top do, what does the bottom do, do they conflict in purpose or just text?”
• Red flag: agent “resolves” by taking one side wholesale without you reading → it guessed intent. Re-run with the prompt above.
• Conflicts are the one place to deliberately slow down an agent session.
